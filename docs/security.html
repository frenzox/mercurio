Authentication & access

Who may connect, and which topics each client may publish, subscribe to and receive.

Mercurio offers several ways to authenticate clients and decide their access. They combine as follows:

NeedUse
A fixed list of userspassword file and ACL file
Users and access managed while the broker runsdynamic security
Users kept in your own database or identity serviceHTTP authentication
Devices identified by certificatesclient certificates, with an ACL file
Custom logic in Rustthe server library's traits

Password files

[auth]
enabled = true
allow_anonymous = false
password_file = "/etc/mercurio/passwd"

With enabled = true, clients must send a user name and password found in password_file. With allow_anonymous = true, clients that send no user name are let in as anonymous; credentials that are sent are always checked.

The file holds one user:hash line per user. Manage it with mercuriod passwd, which writes Argon2 hashes:

# Add a user, or change their password (prompts for it)
mercuriod passwd -f /etc/mercurio/passwd -u alice

# Remove a user
mercuriod passwd -f /etc/mercurio/passwd -u alice -d

mercuriod passwd replaces the file in one step, so a reload never sees half of it. The file keeps its owner, group and mode, at most 0640; a new file gets 0600, so let the broker read it with chgrp mercurio and chmod 640. A file it cannot read in full, such as one with a malformed line, is left unchanged with an error.

Files written by mosquitto_passwd work unchanged: their $7$ (PBKDF2-SHA512, mosquitto 2.0's default) and $6$ (SHA-512, older versions) hashes are recognised.

Access control lists

[auth]
acl_file = "/etc/mercurio/acl"

The file follows mosquitto's acl_file format, so existing files can be reused:

# Rules before any `user` line apply to anonymous clients
topic read public/#

user alice
topic readwrite alice/#
topic deny alice/secret

# Patterns apply to every client; %u is the user name, %c the client id
pattern write devices/%c/status
pattern read users/%u/inbox
  • The access is read, write, readwrite (the default) or deny. read covers subscribing and receiving; write covers publishing.
  • Anything not granted is denied, and deny overrides any grant.
  • A subscription is allowed only when a rule covers its whole filter: a client granted sensors/+/temperature may subscribe to it, but not to sensors/#.
  • Shared subscriptions are checked by their topic filter: $share/group/sensors/+/temperature needs the same grant as sensors/+/temperature.
  • user rules only apply to user names verified by authentication. Other clients are matched as anonymous.
  • A will counts as a publish: a client whose will topic it may not publish to is refused at CONNECT.

An ACL file works without passwords too, for example with client certificates.

$SYS topics only accept the broker's own statistics. $CONTROL topics, which administer the broker, are refused to every client unless an ACL file, dynamic security or an HTTP ACL endpoint grants them. Administration lists the grants its commands need; clients of the admin socket need none.

TLS and client certificates

[server.tls]
enabled = true
cert_path = "/etc/mercurio/server.crt"
key_path = "/etc/mercurio/server.key"

# Require client certificates signed by this CA
ca_path = "/etc/mercurio/ca.crt"
# Refuse revoked ones
crl_path = "/etc/mercurio/crl.pem"
# The certificate names the client
identity_as_username = true
# Refuse TLS 1.2
min_version = "1.3"
  • With ca_path, clients must present a certificate signed by that CA, or the handshake fails.
  • crl_path refuses certificates revoked in the given CRLs.
  • identity_as_username makes the certificate's Common Name the client's user name. The client counts as authenticated, the user name and password in CONNECT are ignored, and user rules in the ACL file apply to it.
  • subject_as_username uses the whole subject instead, in RFC 2253 form as mosquitto and OpenSSL print it, such as CN=alice,O=Acme\, Inc,C=PT.

A device fleet authenticated by certificates alone:

[server]
host = "0.0.0.0"
port = 8883

[server.tls]
enabled = true
cert_path = "/etc/mercurio/server.crt"
key_path = "/etc/mercurio/server.key"
ca_path = "/etc/mercurio/devices-ca.crt"
identity_as_username = true

[auth]
enabled = true
allow_anonymous = false
acl_file = "/etc/mercurio/acl"
# /etc/mercurio/acl: each device writes its own telemetry
pattern write devices/%u/telemetry
pattern read devices/%u/commands

Each listener has its own TLS settings; see Listeners.

Dynamic security

Dynamic security manages clients, roles and access while the broker runs, with the JSON commands of mosquitto's dynamic security plugin. It replaces password_file and acl_file.

# Create the state file with an administrator (prompts for the password)
sudo mercuriod dynsec-init -f /var/lib/mercurio/dynamic-security.json -u admin

The file is created with mode 0600. Run as root in a directory owned by another user, as the service's state directory /var/lib/mercurio is, dynsec-init gives the file to that directory's owner and group, so the service can read it. systemd creates that directory when the service first starts: start it once before, with systemctl start mercuriod, if it has never run.

[auth]
enabled = true
allow_anonymous = false
dynamic_security = "/var/lib/mercurio/dynamic-security.json"

Manage it with mercurioctl, on the broker's host through the admin socket, or from anywhere as the administrator:

# On the broker's host, as root or a member of the mercurio group
mercurioctl dynsec create-role sensor
mercurioctl dynsec add-role-acl sensor publishClientSend 'sensors/#' allow
mercurioctl dynsec create-group sensors --role sensor
mercurioctl dynsec create-client s1 --group sensors   # asks for the password

# From another machine
mercurioctl -H broker.example.com -u admin dynsec list-clients

Underneath, these are JSON commands published to $CONTROL/dynamic-security/v1, with the names and arguments of mosquitto's plugin. They use the same envelope and replies as the broker's own commands. Failed commands carry an error, without a code.

Only clients of the admin socket and of listeners that use the main [auth] can send commands: a listener with its own [listeners.auth] doesn't include dynamic security.

Model

  • Clients log in with a user name and password, and can be disabled. A client created with a clientid may connect only with that client id, not with one the broker assigns. A user name dynamic security has no client for, such as one taken from a certificate with identity_as_username, gets no access at all: create a client of that name, without a password, to give it roles. A client deleted while connected loses its access at once.
  • Roles hold ACLs. A client has its own roles and those of its groups.
  • Groups give their roles to their members. The anonymous group's roles apply to clients without a user name.
  • ACLs have a type, a topic filter, an optional priority and allow. The matching ACL with the highest priority decides.
ACL typeDecides
publishClientSendPublishing
publishClientReceiveReceiving messages
subscribePatternSubscribing to filters covered by the topic
subscribeLiteralSubscribing to exactly the topic

Without a matching ACL, only receiving is allowed, as in mosquitto. setDefaultACLAccess changes that, with publishClientSend, publishClientReceive and subscribe.

Commands

AreaCommands
ClientscreateClient, deleteClient, setClientPassword, enableClient, disableClient, addClientRole, removeClientRole, getClient, listClients
RolescreateRole, deleteRole, addRoleACL, removeRoleACL, getRole, listRoles
GroupscreateGroup, deleteGroup, addGroupRole, removeGroupRole, addGroupClient, removeGroupClient, getGroup, listGroups, setAnonymousGroup, getAnonymousGroup
DefaultssetDefaultACLAccess, getDefaultACLAccess

Changes take effect at once and are saved to the file after each message. As in mosquitto, a change that can take access away disconnects the connected clients it concerns, with reason code Administrative Action (0x98) and without their wills, so they log in again under their new access: deleting or disabling a client or setting its password, adding or removing a client's roles or groups, adding or removing a group's roles, deleting a group or a role, and adding or removing a role's ACLs. Changes to the anonymous group disconnect anonymous clients that came over the network; in-process clients and those of Unix sockets stay connected. The file is replaced in one step, so a crash never leaves it half written.

HTTP authentication

Delegates checks to an HTTP service, with the requests of mosquitto-go-auth's HTTP backend, so services written for it answer Mercurio too.

[auth]
enabled = true
allow_anonymous = false

[auth.http]
user_url = "https://auth.internal/mqtt/user"
acl_url = "https://auth.internal/mqtt/acl"
timeout_seconds = 5
cache_seconds = 30
EndpointRequest body
user_url, at each login{"username": "alice", "password": "...", "clientid": ""}
acl_url, at each topic check{"username": "alice", "clientid": "c1", "topic": "a/b", "acc": 2}

acc is 1 to receive, 2 to publish and 4 to subscribe. A 2xx status allows and a 4xx status denies. Topic answers are reused for cache_seconds, since every message is checked. Any other status, an error or a timeout also denies, but is not cached, so the check is asked again once the service is back; the broker logs these failures at warn, at most once every 10 seconds. At most 32 requests run at once, and identical checks made while one is out wait for its answer. A user_url that is plain http:// to another host is logged at startup, as passwords then cross the network unencrypted. user_url replaces password_file, and acl_url replaces acl_file; either can be used alone.

A minimal service, in Python:

from http.server import BaseHTTPRequestHandler, HTTPServer
import json

class Auth(BaseHTTPRequestHandler):
    def do_POST(self):
        body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        if self.path == "/mqtt/user":
            ok = body["username"] == "alice" and body["password"] == "secret"
        else:
            ok = body["topic"].startswith(f"{body['username']}/")
        self.send_response(200 if ok else 403)
        self.end_headers()

HTTPServer(("127.0.0.1", 8000), Auth).serve_forever()

MQTT 5 enhanced authentication

MQTT 5 clients can authenticate with a method such as SCRAM through the AUTH packet, and re-authenticate during a connection. The daemon has no method configured; applications embedding the broker register methods through the server library. See Embedding.

Client id ownership

A client id belongs to the owner of its session for as long as that session exists, connected or not. The owner is the user the client authenticated as, or anonymous, together with the mount point of its listener. A client of the same owner takes over the id as usual: the connection that held it closes with Session Taken Over. A client of another owner is refused with Not Authorized (return code 5 in MQTT 3.1.1), Clean Start or not, and the connection, session, queued messages and will of the owner stay as they were. The broker logs each refusal at warn level with the client id and both owners.

A session left by a previous owner blocks the id until it expires. To give the id to someone else sooner, delete the session with mercurioctl client delete-session <clientid>.

Reloading

Send SIGHUP, or run systemctl reload mercuriod, to reread every password file, ACL file and dynamic security file, those of listeners included, without dropping connections. mercurioctl broker reload does the same and reports how each file went.

  • New ACL rules apply to every later publish, subscribe and delivery, connected clients included.
  • Password changes apply to later logins.
  • If a file fails to load, the broker logs the error and keeps the previous version, so a typo never locks everyone out.
  • Other settings need a restart.

Plugin sandbox

WebAssembly plugins run with no files, no environment and no network, except the HTTP hosts and socket addresses listed in allow_http and allow_sockets. Their standard output and error are discarded; they log through the broker, and a Rust plugin's panic messages are logged at error level. Each call has a time limit and each copy a memory limit. A plugin that fails or runs out of time denies, for authentication and access control, and drops, for messages. See WebAssembly plugins.

Per-listener authentication

A listener can have its own [listeners.auth], replacing [auth] for its clients: for example, open access on a localhost listener and passwords on the public one. See Listeners.
