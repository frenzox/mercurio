Command-line client

recado pub publishes a message, recado sub prints messages until interrupted. Both work with any MQTT broker.

To administer a broker, use mercurioctl.

Publishing

# A message, at QoS 1
recado pub -t sensors/kitchen -m 21.5 -q 1

# From standard input
echo '{"temp": 21.5}' | recado pub -t sensors/kitchen --content-type application/json

# A binary file, such as an image or a firmware image
recado pub -t cameras/door/snapshot -f snapshot.jpg

# Retained, so new subscribers get it at once
recado pub -t status/door -m open -r

# An MQTT 5 request, with properties
recado pub -t requests/lamp -m on --response-topic replies/me \
    --correlation-data 42 --user-property source=cli --message-expiry 60
OptionMeaning
-t, --topicTopic to publish to (required)
-m, --messagePayload, as text. Without it or -f, standard input is published byte for byte
-f, --file PATHPublish the contents of a file, binary or not
-q, --qos0, 1 or 2 (default 0)
-r, --retainRetain the message on the broker
--content-typeContent type of the payload, such as a MIME type
--response-topicTopic a reply should be published to
--correlation-dataData that ties a reply to its request
--message-expirySeconds the broker keeps the message for subscribers yet to get it
--utf8Mark the payload as UTF-8 text
--user-property key=valueUser property; may be repeated

Subscribing

# Print payloads, with their topics
recado sub -t 'sensors/#' -T

# Several filters
recado sub -t 'sensors/#' -t 'alerts/#' -T

# A persistent subscriber that survives broker restarts and network loss
recado sub -t 'alerts/#' -i monitor -c -x 3600 --reconnect 5 -q 1

# With a will, published if the subscriber disappears
recado sub -t 'cmd/#' --will-topic status/monitor --will-message offline --will-retain
OptionMeaning
-t, --topicTopic filter; may be repeated (required)
-q, --qosQoS of the subscriptions (default 0)
-T, --print-topicPrint the topic and : before each message
--no-localDon't receive messages this client publishes itself
--retain-as-publishedKeep the retain flag messages were published with
--retain-handlingRetained messages on subscribing: 0 always, 1 only for new subscriptions, 2 never
--subscription-idIdentifier the broker attaches to messages matching these subscriptions
--reconnect SECONDSReconnect after losing the connection, waiting this long between attempts
--will-topic, --will-messageWill published by the broker if the client disconnects unexpectedly
--will-qos, --will-retain, --will-delayQoS, retain flag and delay (MQTT 5) of the will

Connection options

Both commands take these:

OptionMeaningDefault
-H, --hostBroker host namelocalhost
-p, --portBroker port1883
--unix PATHConnect through this Unix socket instead of TCP; not with -H, -p or the TLS options
-i, --client-idClient idgenerated
-u, --username, -P, --passwordCredentials. The password can also come from RECADO_PASSWORD, which other users can't see in ps; -u alone asks for it when standard error is a terminal
-k, --keep-aliveKeep-alive, in seconds60
-c, --no-clean-startKeep the session after disconnecting
-x, --session-expirySeconds the broker keeps the session after the connection closes (MQTT 5)0
-V, --protocol-version5, 311 or 31; also 3.1.1, 3.1 and mosquitto's mqttv5, mqttv311, mqttv31. Anything else is an error5
--tlsConnect with TLS
--cafileCA certificate to verify the broker with; implies --tlssystem roots
--insecureSkip certificate verification, for testing only; implies --tls
-v, --verboseVerbose output
# Over TLS, as alice; asks for the password
recado sub -H broker.example.com -p 8883 --cafile ca.crt -u alice -t '#'

# In a script, with the password out of ps
RECADO_PASSWORD="$(cat ~/.mqtt-password)" recado pub -u alice -t status -m up

# MQTT 3.1.1
recado pub -V 311 -t test -m hello

# Through a Unix socket listener
recado sub --unix /run/mercurio/mqtt.sock -t 'sensors/#' -T

Exit status

recado uses the same exit statuses as mercurioctl:

StatusMeans
0Success, or sub stopped by Ctrl-C or by its reader going away
1The broker refused a subscription, or a QoS 1 or 2 message; the message names the filter and the reason
2The broker couldn't be reached, refused the login, or closed the connection; with --reconnect, when the client gives up
3Wrong usage, such as an unknown option or a QoS above 2

Messages and logs go to standard error, so standard output carries only the payloads.
