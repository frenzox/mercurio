Embedding the broker

mercurio-server is the broker as a library: run it inside your own program, with your own authentication, access control and storage.

Adding it

[dependencies]
mercurio-server = "0.5"
mercurio-storage = { version = "0.3", features = ["sqlite"] }
tokio = { version = "1", features = ["full"] }

Running a broker

use mercurio_server::server::{run_with_config, ServerConfig};
use tokio::net::TcpListener;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let listener = TcpListener::bind("0.0.0.0:1883").await?;
    run_with_config(listener, ServerConfig::default(), tokio::signal::ctrl_c()).await?;
    Ok(())
}

The broker runs until the future given last completes, then shuts down gracefully. Three entry points exist:

FunctionUse
run(listener, shutdown)Defaults, state in memory
run_with_config(listener, config, shutdown)Your configuration, state in memory
run_with_storage(listener, config, storage, shutdown)Your configuration and storage

They fail without serving anyone if the configuration can't be used, such as a mount point with a wildcard.

Configuration

ServerConfig mirrors the daemon's configuration file:

FieldHolds
tlsOption<Tls> for the main listener, see below
authAuthConfig: whether authentication is required and anonymous clients are allowed
pluginsVec<Arc<dyn Plugin>>: the plugin chain, see below
plugin_timeoutLongest a plugin hook may take, 5 seconds by default
plugin_tick_intervalHow often Plugin::on_tick runs, 1 second by default
limitsLimits: connection, packet, queue and QoS limits
policyConnectPolicy: client id rules, redirection, response information
listenersExtra ListenerConfigs: TCP or Unix sockets, MQTT or WebSocket, with their own TLS, mount point, auth, plugins and limits
local_listenerIn-process connections, see below
admin_extensionServes the $CONTROL/broker/v1 commands the broker doesn't know, see below
sys_intervalHow often $SYS statistics are published
use mercurio_server::{
    server::{ListenerConfig, ServerConfig, Transport},
    tls::{Tls, TlsConfig},
};
use tokio::net::TcpListener;

let tls = Tls::new(TlsConfig::new("server.crt", "server.key"))?;
let mut tls_listener =
    ListenerConfig::new(TcpListener::bind("0.0.0.0:8883").await?, Transport::Mqtt);
tls_listener.tls = Some(tls.clone());

let mut config = ServerConfig::default();
config.listeners.push(tls_listener);

TLS

Tls::new reads the certificate, key, CA and CRL files a TlsConfig names, and fails if they can't be used. Tls::reload reads them again, for example after a certificate is renewed: connections from then on get the new files, and those already up keep theirs. A reload that fails returns the error and keeps the previous files. Clones of a Tls share it, so one reload reaches every listener given a clone.

For settings TlsConfig has no field for, such as ALPN, session resumption, a certificate resolver or a client verifier of your own, build a rustls::ServerConfig and serve it with Tls::from_rustls(config, username_from_certificate). Reloading is then up to you: Tls::reload returns an error, and Tls::set_server_config swaps in a new configuration for later connections. With a CertificateName, clients that present a certificate are named by it; whether they must present one is up to your client verifier.

Configuration types are built from their default, or from a constructor such as ListenerConfig::new, then changed field by field: new fields may appear in minor releases, so they can't be written out as struct literals.

Plugins

One Plugin trait covers authentication, MQTT 5 enhanced authentication, topic access control, message hooks, lifecycle events, periodic work and $CONTROL commands. A plugin implements the hooks it needs; every other one does nothing. The broker runs its plugins as a chain, in the order configured:

  • Plugin::authenticate and Plugin::authorize: the first Decision::Allow or Decision::Deny decides, and Decision::Defer asks the next plugin. Credentials are checked whenever a client sends them, even with require_auth off, so a plugin's Deny always refuses them. When every plugin defers, a client with credentials is refused if require_auth is on and let in unverified if not, an anonymous one follows allow_anonymous, and access is allowed.
  • Plugin::authorize_control: decides who may publish to $CONTROL/..., which administers the broker, in place of authorize. It is a separate question, so a plugin that allows every topic doesn't make every client an administrator. It chains like authorize, but when every plugin defers, the client is refused. Requests to $CONTROL/broker/v1 are asked about that topic, then about each command as $CONTROL/broker/v1/<command>. Subscribing to and receiving $CONTROL topics stay with authorize, as answers go only to the client that asked.
  • Plugin::on_message: every plugin, each seeing the changes of the ones before; the first MessageAction::Drop drops the message. Changes are trusted: a new topic isn't checked against access control, and a changed retain or qos isn't checked against the retain and QoS limits. The exception is a message moved to a different topic that starts with $, such as $SYS/... or $CONTROL/...: it is dropped, still acknowledged, with a warning in the log.
  • Plugin::on_event and Plugin::on_tick: every plugin.

Each hook call has a time limit, ServerConfig::plugin_timeout. A hook that runs out of time or panics denies, for authentication and access control, and drops, for messages. A listener can have its own chain in ListenerConfig::plugins; ListenerConfig::auth only sets require_auth and allow_anonymous for it.

use std::sync::Arc;

use mercurio_server::{
    plugin::{ready, Access, BoxFuture, ClientInfo, Credentials, Decision, Plugin},
    server::ServerConfig,
};

/// Lets each user use the topics under their own name.
struct OwnTopics;

impl Plugin for OwnTopics {
    fn name(&self) -> &str {
        "own-topics"
    }

    fn authenticate<'a>(
        &'a self,
        _: &'a ClientInfo,
        credentials: &'a Credentials<'a>,
    ) -> BoxFuture<'a, Decision> {
        // A real plugin would check a database here, and could await it
        let known = matches!(
            (credentials.username, credentials.password),
            ("alice", b"alice-secret") | ("bob", b"bob-secret")
        );
        ready(if known { Decision::Allow } else { Decision::Deny })
    }

    fn authorize<'a>(
        &'a self,
        client: &'a ClientInfo,
        topic: &'a str,
        _: Access,
    ) -> BoxFuture<'a, Decision> {
        let own = client
            .username
            .as_deref()
            .is_some_and(|user| topic.starts_with(&format!("{user}/")));
        ready(if own { Decision::Allow } else { Decision::Deny })
    }
}

let mut config = ServerConfig::default();
config.auth.require_auth = true;
config.plugins = vec![Arc::new(OwnTopics)];
  • Access is Write to publish, Subscribe to subscribe, with the topic filter, and Read to receive a message.
  • ClientInfo::username is only set for users the broker verified. client_id is empty in authenticate when the client asked the server to assign one.
  • authorize runs for every message, so keep it fast; a hook that is ready at once, as above, costs no timer. Cache answers that need I/O.
  • Plugin::on_control handles publishes to $CONTROL/<name>/.... Its answer goes only to the client that sent the request: on the request's Response Topic, with its Correlation Data, or on $CONTROL/<name>/<path>/response without one.
  • A client publishing to $CONTROL/<name>/x/response reaches Plugin::on_control with path x/response; plugins that only answer requests should ignore such paths.
  • auth::SimpleCredentialValidator checks a list of users held in plaintext, for tests and demos; it leaves users it doesn't hold to the next plugin. acl::AclFile::parse reads mosquitto's ACL format, if you want it from your own code.

Enhanced authentication

A plugin takes part in MQTT 5 enhanced authentication by returning an AuthExchange from Plugin::begin_auth for the methods it knows. begin_auth gets the client: during CONNECT its user name is the one the client claims, if any; on re-authentication it is the verified user. The broker calls step once per message from the client; each step returns AuthResult::Continue(challenge), Success { username, data } or Failed(reason). data, such as SCRAM's final server message, goes to the client as Authentication Data in the CONNACK, or in the AUTH that ends a re-authentication. auth::PlainAuth is a complete example, with passwords held in plaintext for tests and demos: add it to ServerConfig::plugins to accept the PLAIN method.

Storage

use std::sync::Arc;

use mercurio_server::server::{run_with_storage, ServerConfig};
use mercurio_storage::sqlite::SqliteStore;

let storage = Arc::new(SqliteStore::new("/var/lib/myapp/mqtt.db")?);
run_with_storage(listener, ServerConfig::default(), storage, shutdown).await?;

Any type implementing the storage traits of mercurio-storage (sessions, retained messages, wills, in-flight messages and queues) can replace SQLite; postgres::PostgresStore::connect_exclusive(url, &options, wait), behind the postgres feature, keeps it in PostgreSQL; postgres::ConnectOptions sets the CA certificate and the size of its connection pool. It returns a DatabaseLock along with the store: only its holder may write to the database, and its lost() completes when another broker may have taken over, the moment to stop serving.

In-process clients

A LocalConnector opens connections to the broker in memory, without TCP. Combined with mercurio-client's connector option, it lets your program publish and subscribe on its own broker. These connections are trusted: authentication and access control don't apply to them.

use mercurio_client::{ConnectOptions, MqttClient, QoS};
use mercurio_server::server::{run_with_config, LocalConnector, ServerConfig};

let (connector, local_listener) = LocalConnector::new();
let mut config = ServerConfig::default();
config.local_listener = Some(local_listener);
tokio::spawn(run_with_config(listener, config, std::future::pending::<()>()));

let options = ConnectOptions::new("localhost", 0)
    .client_id("internal")
    .connector(move || std::future::ready(connector.connect()));
let client = MqttClient::connect(options).await?;
client.publish("app/started", "1", QoS::AtLeastOnce).await?;

The daemon's bridges and dynamic security work this way.

Administering it

Server separates setting a broker up from serving it. In between it hands out an Admin, which runs the commands of the admin API as async methods, before and while the broker serves. The run* functions above are shortcuts for Server::new followed by Server::run.

use std::sync::Arc;
use mercurio_server::{admin::ClientQuery, server::{Server, ServerConfig}};
use mercurio_storage::memory::MemoryStore;

let server = Server::new(listener, ServerConfig::default(), Arc::new(MemoryStore::new())).await?;
let admin = server.admin();
tokio::spawn(server.run(tokio::signal::ctrl_c()));

let mut query = ClientQuery::default();
query.connected = Some(true);
for client in admin.clients(&query).await.items {
    println!("{} {:?}", client.client_id, client.address);
}
  • Methods return plain structs. Failures are an AdminError, whose code is the protocol's.
  • The broker serves the same commands over MQTT on $CONTROL/broker/v1, to clients access control allows. ServerConfig::admin_extension takes an AdminExtension for commands the broker doesn't know: mercuriod adds its bridge, configuration, log level and reload commands this way. Without one, those answer unavailable.
  • A ListenerConfig on a Unix socket can be trusted: its clients skip authentication and access control, and run every command. Give it a peer_filter to choose clients by their user and group ids, as mercuriod's admin socket does, or keep the socket's permissions tight. Server::new refuses a trusted listener on TCP, with its own authentication or plugins, with proxy_protocol or serving WebSocket.

Logs

The broker logs through tracing. Install any subscriber, such as tracing_subscriber::fmt().init(). Connection and disconnection messages use the target mercurio::connections, the constant mercurio_server::CONNECTIONS, so they can be filtered alone.
